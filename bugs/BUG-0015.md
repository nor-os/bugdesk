## Description

A new record gets `max(id) + 1` from the files in the folder. Two branches or
machines that each file a bug before merging both produce, say, `BUG-0016.md`;
git then reports an add/add conflict at best, and at worst one record silently
replaces the other. Same for backlog items.

Options: detect a duplicate id on load and renumber on the next write, reserve
ids in a committed counter file (conflicts the same way, but loudly), or give
ids a short collision-resistant suffix. Whatever is chosen has to keep
hand-written `BUG-NNNN.md` names working.

Found while reviewing storage and indexing; see the record cache work (BUG-0014).

### 2026-10-05T20:01Z · norman_agent (status: investigation -> testing)

Of the three options, I took a fourth that keeps every file name as it is: **a
new id is one above every id this checkout has ever seen for the store**, not
just the folder's highest. Fixed in 64fa262 (`server/RecordIds.cs`).

"Ever seen" means the highest of:
- the files in the folder;
- every file of that kind ever **added on any ref git knows** (local
  branches, fetched remote branches, and history, so deleted records count),
  read with one `git log --all --diff-filter=A` at the moment a record is
  created;
- the store's **trash** (records deleted through BUG-0012).

This covers two cases. A bug filed and pushed on another branch is skipped
over once you have fetched. And an id never comes back after its record was
deleted or moved away, which is exactly what happened in this store: our
BUG-0011…0015 reuse ids that belonged to records moved to Tables in 80551f5.
Without git (no repository, git not installed, or slower than 5 s) it falls
back to the folder plus the trash, which is the old behaviour.

What it cannot do: two branches that both file a record **before either has
pushed** still pick the same number. Nothing short of a server or random ids
can coordinate that. Git then reports an add/add conflict, which is loud rather
than silent.

The `/bugs` and `/backlog` skills now allocate ids the same way, so agents
stay consistent with the server.

I tested it on a scratch repo. With BUG-0001…0004 on disk, BUG-0005 deleted in
history and BUG-0009 on another branch, a new bug got **#10**; the old rule
gave #5. After deleting #10 the next bug got #11, and outside git the rule
falls back to folder + 1. Tracker 34/34, UI 218/218; the server builds with 0
warnings.

Side note: STORY-0008 (the DataTable story I filed today) and your
STORY-0009 also reuse old ids (STORY-0008…0011 went to Tables). Per the rules
I have not renumbered them; say if you want it done.
