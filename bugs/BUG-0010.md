## Description

Right now hitting the rate limit just returns a bare `429` with no body, which
leaves API consumers guessing. Should return something a client can actually
act on.

## Comments

### 2026-07-30 · agent

Proposed response body for the 429:

```json
{
  "error": "rate_limited",
  "retryAfterSeconds": 42,
  "limit": 100,
  "window": "1m"
}
```

Plan:

- Add a `Retry-After` header alongside the JSON body (some clients only look
  at the header, some only at the body — cover both).
- Compute `retryAfterSeconds` from the actual sliding window state rather than
  a hardcoded constant, so it's accurate under load.
- Leave the `429` status code itself unchanged — this is purely about making
  the response body useful, not changing the rate-limit behavior.

Related to #5 (the webhook-retry regression) only in that both touch the
retry/backoff code path, not because they share a root cause.
