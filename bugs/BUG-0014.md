### 2026-10-05T19:45Z · norman_agent (status: investigation -> testing)

Your guess was right. Switching project reloads the page, and the page's four
record calls (bugs, meta, backlog, backlog meta) **each re-read and re-parsed
every file in the store**. The backlog calls also walked the tree with
linear scans. On Montanha OS (538 bugs, 1,022 backlog items) that is the slow
part.

Fixed in 422d393 with a record cache (`server/RecordCache.cs`):

- Records are parsed once and kept in memory, and mirrored to
  `.bugdesk/cache/*.json` so a restart doesn't re-parse either. The cache folder
  ignores itself in git and is safe to delete.
- The files stay the only source of truth. Every lookup checks each file's
  modified time and size and re-reads only the ones that changed, so edits from
  vim, `git pull` or an agent show up at once. I checked: edits, a new file, a
  deleted file, five same-size edits within one second, and an edit made while
  the server was stopped.
- Tree walks (ancestors, descendants, inherited phase and due date) use an id
  and parent index.

Measured with native Windows servers on the real Montanha OS folders, in
headless Edge:

| | before | after |
|---|---|---|
| each record call (warm) | 170–370 ms | 10–40 ms |
| page ready, warm switch | 656 ms | 333 ms |
| page ready, first open | 1,268 ms | 1,017 ms |

Even before the fix that is not "an eternity", so something on your instance
may add more than I could reproduce: your saved layout with its open tabs,
the tracker, or the other projects. My test had none of those.

To test: **restart your server**, because this change is server-side. Switch to
Montanha OS twice; the second switch is the warm case. If it is still slow,
reopen this and say which project and roughly how long it takes; I'll measure
against your real setup next.
