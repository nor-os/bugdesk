### 2026-10-05T19:33Z · norman_agent (status: investigation -> testing)

Reproduced in the table component itself, not in the data. Filtering and
sorting always ran over every row, but **a sort kept you on the page you were
on**: on page 3 of 250 rows, sorting descending showed rows 50…1 — the third
page of the new order — which looks exactly like "it only sorted this page".

There was a second way to see it: an ad-hoc view (a rail or Inspector click)
and the search results all share one remembered table slot, and the remembered
**page** came back with it, so a new filter's results could open on page 2 of
2.

Fixed in 9936b17:

- `DataTable.sortBy` goes back to the first page.
- A new `persistPage` option; the bug queue and the backlog board turn it off for
  ad-hoc views, and search results turn it off always. Saved and built-in views
  still reopen on the page you left, as before.
- Two regression tests in `scripts/test-dom.mjs` (139/139 green).
- The same `sortBy` fix is in FlexDesk's own DataTable
  (`../FlexDesk/src/ui/components/data_table.js`, tests green). It is not
  committed, built or published, because FlexDesk has other uncommitted work in
  its tree.

To test: open a list with more than 100 rows, go to page 2 or 3 and click a
column header. The strip should read "1–100 of N", and the first row should be
the first in the new order. Then click a rail filter and check that it starts
on page 1.

Not changed: in the backlog **tree**, a column filter does not search inside
collapsed items. Their children are not rows until expanded. Say if you want
filtering to expand them.
